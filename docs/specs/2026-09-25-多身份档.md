# 多身份档（identity profiles）

日期：2026-09-25　术语见 `CONTEXT.md`　形态决策见 `docs/adr/0001-profiles-as-sibling-directories-envelope-stays-v1.md`

## 1. 问题陈述

现在整个应用只有一个身份档：一把主密码、一个 `vault.pvlt`、一个会话。用户想把工作、个人、测试用的凭据分隔开，各自的库有各自的口令，解锁其中一个时**看不到其他任何内容**——不是"标签筛选后隐藏"，而是另一些条目在密文层面就不属于当前会话。

现有实现里三处单值假设决定了这不是加个字段能解决的：

- `VaultService` 只有 `this.session` 一个会话槽（`server/vault.ts:44`）
- 库文件名固定 `vault.pvlt`，且所有落盘路径都从 `this.directory` 派生：写锁 `vault.write-lock`（`:141`）、临时文件 `.vault-<uuid>.tmp`（`:151`）、恢复安全副本 `before-restore-*.pvlt`（`:160`）
- `StorageLocation.load()` 启动时硬要求 `<目录>/vault.pvlt` 存在，不存在即拒绝启动（`server/storage-location.ts:61-66`），`assertCurrent()` 每个请求再验一遍（`:81-87`）

## 2. 方案概述

一个存储目录下并存多份**独立的 version 1 信封**：默认身份档继续住 `<目录>/vault.pvlt`（现有数据一字节不动），新建身份档住 `<目录>/<名字>/vault.pvlt`。

服务端把"当前目录"从常量变成**按当前身份档解析**的属性，其余写盘逻辑（原子写、写锁、指纹哨兵、恢复副本）原样复用，只是换了一个基准目录。会话仍是全局唯一的一个槽，只是多记一个"当前是哪个档"。

客户端在登录页做档列表与选择，进入应用后与今天几乎一致。

## 3. 用户故事

每条都可独立验证。括号里标注验证它的接缝（见第 5 节）。

### 首次使用与创建

1. 存储目录里一个身份档都没有时，登录页显示现有的"创建我的保管库"表单（设置主密码 + 确认），不要求先起名。（A、B）
2. 新建身份档表单要求：名字 1–32 字（去首尾空白）、口令 ≥12 字、确认口令。三者任一不满足时给出对应提示，不发起请求。（A、B）
3. 名字含 `/` `\` `..`、Windows 非法字符 `<>:"|?*`、控制字符，或以 Windows 保留名（con/prn/aux/nul/com1…/lpt1…）开头或成段 → 拒绝创建。（A）
4. 名字与已有档**按大小写折叠和 Unicode 规范化后**判重（Windows 文件系统大小写不敏感，只按精确大小写判重会造出一个"建得出来读不回来"的档）→ 拒绝创建并提示重名。（A）
5. 身份档总数（含默认档）达到上限 16 后，"新建身份档"不可用并说明原因。（A）
6. 创建只落盘一个新目录和一个新 `vault.pvlt`，不触碰任何其他档的文件。（A）
7. 未解锁任何档时就能新建身份档——不需要先解锁另一个档。（A、B）

### 登录、切换与锁定

8. 登录页列出所有身份档（显示名；未解锁的档不显示任何内容线索），并让用户选中其一后输口令。条目数**不放在登录页**：条目在密文内，未解锁读不到，而把它另存明文等于泄露"这个档是空的、那个档有 40 条"这类活动元信息，与本功能的隔离目标相逆。条目数只在解锁后的侧栏计数里出现（今天的行为）。（A、B）
9. 选中一个档输对口令 → 进入该档；输错 → 提示主密码不正确，输入框清空。（B）
10. 口令尝试节流按**身份档独立**计数：在 A 档连错不会让 B 档暂时锁死，反之亦然。（A）
11. 已解锁时切换到另一个档 = 先锁定当前档（未保存草稿丢弃、旧令牌立即失效），再解锁目标档。（A、B）
12. 全局同一时刻只有一个档处于解锁状态；第二个浏览器标签解锁另一个档时，会把第一个标签的会话顶掉（沿用现有"新会话使先前异步工作全部作废"的语义，`src/App.tsx` 的 `epoch`/`isCurrent` 机制）。（A、B）
13. 自动锁定、活动续期、离开页面即锁、会话到期，作用对象是当前解锁的那个档，行为与今天逐条一致。（A、B）
14. 解锁后界面某处显示当前身份档名。（B）
15. 默认档的显示名可以在设置页改（存应用配置，磁盘路径不变）；非默认档不提供改名入口，界面上说明"档名即目录名，建档后不可改"。（A、B）

### 条目操作

16. 列表、搜索、分类计数、新增/编辑/删除、复制密码，全部只作用于当前解锁的档。（A、B）
17. 在一个档里搜索另一个档的条目名 → 搜不到。（A、B）
18. 各档的条目 id 各自独立生成，跨档重复不构成冲突。（A）

### 删除身份档

19. 非默认档在**已解锁该档**时可以从设置页删除；未解锁的档在任何界面都没有删除入口。（A、B）
20. 删除需要二次确认：输入该档的名字才能按下确认按钮。（B）
21. 删除前把该档的 `vault.pvlt` 复制成同目录下的 `before-delete-<时间>-<uuid>.pvlt`，并在界面上显示这个副本路径与"它仍可用当前口令解开"。（A、B）
22. 默认档不可删除。（A）
23. 删除只移除该档目录内的 `vault.pvlt`、`vault.write-lock` 和残留临时文件；目录下无关的第三方文件保留，目录本身留空待用户清理。（A）

### 备份与恢复

24. "导出备份"只导出当前解锁档的那一个 `vault.pvlt`，下载文件名带身份档名。（A、B）
25. "恢复"只覆盖当前解锁的档，覆盖前照旧生成 `before-restore-*.pvlt`。（A、B）
26. 未解锁任何档时不再提供恢复入口；想把旧备份变成一个新档 = 新建档 → 解锁 → 恢复。（A、B）
27. 旧格式的单个 `vault.pvlt` 备份文件在升级后仍能正常导入默认档。（A、B）

### 存储位置迁移

28. "修改存储位置"仍是全局一个目录：整栋搬家，把默认档文件和所有身份档子目录一起迁到新目录下，保持相对结构。（A）
29. 目标目录里已存在 `vault.pvlt`，或存在任何与现有档同名且内含 `vault.pvlt` 的子目录 → 拒绝迁移，不改配置、不覆盖、不部分搬。（A）
30. 迁移中断/失败时回滚到原目录，各档内容与迁移前一致。（A）

### 启动与配置损坏

31. 存储目录里**还剩着某个身份档**、但默认档不在时（只建过非默认档，或默认档被绕过应用手工删掉），服务照常启动，登录页列出剩下的档，`status.exists` 为假。整棵目录一个库都不剩时**仍然拒绝启动**——那更像是盘没插上而不是全新库，静默当作首次使用会让人在错误的位置建出一个空库。（A）
31b. 每请求的存储哨兵同样只要求"树里至少还有一个库"，不再要求特定于根目录的那一个。（A）
32. 配置 `storage-location.json` 损坏或指向不可访问目录时，仍按今天那样拒绝启动并给出可操作的提示——这一条不变。（A）
33. 扫描身份档时遇到无权限的目录 → 跳过该目录并记录在服务端日志里，不导致整个列表接口失败。（A）
34. 默认档显示名的配置文件损坏时，退回显示"默认"，不影响任何档的解锁。（A）

## 4. 已定决策

不再翻案的取舍，理由在 ADR 与 `CONTEXT.md`。

| 决策 | 内容 |
|---|---|
| 术语 | 新概念叫**身份档**，不叫账号（`EntryType` 的 `'account'` 已表示"网站与应用"条目），也不用"库"指代它 |
| 归属 | 同一个人的多个身份档，地位平等，无主人档/管理员角色 |
| 落盘 | 每档一份独立 version 1 信封；默认档 `<目录>/vault.pvlt` 原地不动，新档 `<目录>/<名>/vault.pvlt` |
| 存在性 | 以磁盘为事实源（档的 `vault.pvlt` 在不在），配置只存默认档显示名 |
| 名字 | 明文、登录页可点选；默认档可重命名，非默认档名即目录名不可改 |
| 会话 | 全局单会话，切档隐含先锁定 |
| 存储位置 | 全局一个目录，整栋搬家 |
| 备份 | 逐档导出、逐档恢复且只能盖当前档 |
| 删除 | 只能删已解锁的非默认档；忘记口令的档留在磁盘上 |
| 首屏 | 无档时沿用现有"创建保管库"流程 |

**被否决的方案**（同样不再重开）：信封内加字段并 bump 到 version 2（旧代码会拒读新文件，且必须给现存数据和全部旧备份写一遍密码学迁移）；多档并存会话（`this.session` 单槽、每请求全库指纹校验、自动锁定时器、pending 槽都要按档索引化，且同时开两档撑大泄露面）；一把总口令带多个档（削弱各档独立口令的意义，一漏全漏）；全档批量打包导出（会造出一个权限大于任何单档的产物，与隔离方向相逆）。

## 5. 测试决策

**不新建接缝。** 复用项目已有的两个：

- **接缝 A（主力）**：`buildApp` + `fixture.api()` 的进程内 HTTP 面（`tests/api.test.ts:43`）。绝大多数故事在这里验证，因为它能同时看到响应码、磁盘目录结构和"另一些字节没被碰到"这一事实。新增 `tests/profiles.test.ts`，直接复用 `withVault` 的 fixture 形状（`directory` / `storagePath` / `now` / `advance` / `restart` / `api`），并扩展出 `profilePath(name)`。
- **接缝 B**：Playwright 端到端（`tests/browser.spec.ts`），只覆盖人的动作路径：首屏建库、登录页列表与选档、新建档、切档先锁、错误口令、删除需输入档名、导出文件名带档名。断言写"改前抓快照、改后比对"，不写死条目数量（serial 套件里前序用例会增删数据）。

**"完成"的判据**：

1. 上述 A 类故事每条至少一条断言；B 类在 Playwright 里跑通。
2. **兼容性硬闸**：现有 80 条单测与 9 条 Playwright 用例**一条都不许改**（除非某条断言正好断言了本 spec 有意改掉的旧行为，那要在 PR 里点名说明是哪条、为什么）。
3. 跨档隔离的反证：解锁 A 档后，用 A 档令牌请求 B 档的 `/api/vault` 等全部会话级端点，一律失败。
4. 磁盘侧证据：创建/删除/迁移后 `readdir` 结果符合预期，其他档文件的字节（指纹）不变。

## 6. 明确不做

- 不做条目在档之间搬迁、复制、合并（本 spec 只加一个"新建后手动重录"的路径）
- 不做档改名（默认档只改显示名）、不做档排序、不做档图标/颜色
- 不做多档同时解锁、不做"总口令"、不做批量打包导出
- 不做忘记口令的找回、恢复码、暴力解锁后门——与项目既有承诺一致
- 不做逐档独立的存储位置
- 不引入 SQLite 之类的索引，不做身份档元数据数据库（磁盘即事实源）
- 不碰前端已有的自动锁定/草稿丢弃/会话竞态防护逻辑，只把"作用对象"从全库改成当前档

## 7. 补充说明（给实现者的坑位提示）

- **`this.directory` 是唯一切点**：把它的读取换成"当前身份档目录"（默认档 → `location.directory`；其他档 → `join(location.directory, name)`），则写锁、临时文件、恢复副本、`readSource`/`atomicWrite` 全部自动跟随。**不要在每个调用点各拼一次路径**，那会漏掉 `before-restore` 的位置。
- **未解锁时没有"当前档"**：`status`、登录、创建、选目录这些无会话操作不能依赖 `this.directory`，需要显式的档位参数；`StorageLocation` 持有的始终是根目录。
- **`session` 要多记两样**：档名/档目录，以及该档的 `fingerprint`、`salt`、`key`。`run()` 里那个每请求指纹哨兵（`server/vault.ts:64-70`）当前只盯默认档，未解锁状态下应当**不检查任何档**，解锁后只检查当前档。
- **节流槽按档独立**：`nextAttemptAt`（`:51`、`private throttle()`）现在是单个全局值，改成按档键控，否则故事 10 不成立。
- **`pending` 恢复槽**要么绑定档、要么在 `clearSession` 时一并作废（现在 `clearSession()` 已经会 `clearPending()`，保持即可，但要注意切档路径必须走到它）。
- **档位参数走哪里**：会话级端点由服务端以"当前档"为准、不信任客户端传来的档名（避免用 A 档令牌读 B 档）；只有 status / create / unlock / 新建档这几个无令牌端点需要显式档标识。默认档的稳定标识建议为 `null` 或 `''`，**不要**用字符串 `'default'`，它会和真实存在的同名目录抢身份。
- **Windows 名字规则**：判重要折叠大小写并做 Unicode NFC 规范化；`storageDirectory()`（`server/storage-location.ts:6-26`）已经有一套目录名校验（保留名、结尾空格句点），新建档的名字校验应与它同源，别写第二份规则。
- **身份档列表不挂在 `/api/status` 上**：`status` 被轮询（会话到期检查、活动续期），把列表挂上去等于每次轮询都要 `readdir` + 逐子目录 `stat`，而这份数据只有登录页用得到。另开无令牌的 `GET /api/profiles`，`VaultStatus` 形状**保持不变**（2026-09-26 修正：原计划改 `VaultStatus` 会必然打破 3 处对整个 status 对象做深度比对的既有断言——`tests/api.test.ts:134`、`tests/storage-location.test.ts:402/408/453`，与"现有测试零修改"的硬闸冲突）。首屏"是不是首次使用"仍由 `status.exists` 判定，不引入新判据。
- **备份下载文件名**：`Content-Disposition` 现在硬编码 `password-vault.pvlt`（`server/app.ts:89`），要带档名就必须做 ASCII/UTF-8 双写（`filename="..."` + `filename*=UTF-8''...`）并过滤控制字符——档名是用户输入。
- **`restart()` 语义**：现有 fixture 的 `restart` 会重新 `StorageLocation.load()`，故事 31/32/34 必须靠它验证，别用直接 new 的方式绕过。
